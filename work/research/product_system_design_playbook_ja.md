# 0からのシステム・プロダクト設計

## 全体像を描き、変更が高くつく判断を見極め、価値の核に投資する

調査・作成日：2026年11月2日  
対象：新規プロダクトや業務システムを設計するソフトウェアエンジニア、プロダクト担当者、小規模チーム

> **提案する方針：問題と全体の構成を先に整理し、後から変えにくい部分を重点的に調べる。既存の仕組みを使って最初の構築を軽くし、自分たちが価値を出す体験・判断・つなぎ方に開発を集中する。**
>
> ここでの「詰める」には、決めることだけでなく、試してから決めること、決定を保留すること、後で変更できる形にすることも含める。

## このレポートの読み方

まず第1・2章で方針と手順を把握し、設計中に第4〜7章の判断基準を参照すると使いやすい。第10章に架空の案件を通した例、第11章に着手時の進め方、第12章にコピーして使えるテンプレートを収めた。

主な前提は、小規模チームによるWebサービス・SaaS・業務アプリの新規開発である。機器制御、既存システムの大規模移行、厳しい安全要件があるシステムでは、検証の量と順番を調整する。特定の技術スタックや開発管理ツールを前提にはしない。

**出典の読み分け。** 本文の出典番号は末尾の一次資料に対応する。企業の公式文書は、その企業が公表する方針・実践の証拠であり、成功の原因や他社での最適解を証明するものではない。DORAの研究に基づく知見も、個々の施策の普遍的な因果効果としては扱わない。手順、判断表、停止条件、テンプレート、架空の例は、資料を組み合わせた本レポートの提案である。日数や件数の例は標準値ではない。

## 1. あなたの価値観に合う設計方針

### 1.1 全体像を先に考えることは、アジャイルと両立する

アジャイルの原則は、変更への対応、動くソフトウェアの継続的な提供に加え、良い設計への継続的な注意と、不要な仕事を増やさない単純さを重視している。最初に何も設計しないことを求めているわけではない。[S01]

あなたの場合は、次のように設計の深さを変えるとよい。

| 対象 | 初期に目指す状態 |
| --- | --- |
| 問題、対象ユーザー、主要な利用の流れ | チームで同じ説明ができる |
| 主要な概念、責任分担、外部との接続 | 全体のつながりと未確認箇所が分かる |
| 変更が高くつく判断 | 根拠、代替案、変更時の負担を確認している |
| 現在の利用に必要な品質 | 守る水準と確認方法が分かる |
| 変えやすい画面・実装の細部 | 最初の利用を成立させる範囲で決める |
| 将来あるかもしれない用途 | 必要性が分かるまで実装を保留する |

Shape Upは、開発前の構想を「細部には余地がある」「主要な要素と接続が考えられている」「投資する範囲が明確」という状態に整える。Linearも、問題の確認、案の探索、大枠と細部を分けたフィードバックを説明している。この二つは、あなたの進め方を具体化するうえで特に参考になる。[S04][S06]

### 1.2 変更が難しい判断ほど、早く向き合う

「早く向き合う」と「早く確定する」は区別して扱う。たとえば外部に公開するデータモデルが重要でも、現場の言葉や使い方が不明なら、先にモデルを凍結するより、代表的なケースを集めて試すほうが判断材料は増える。

Fowlerは、情報が増えるまで判断を延期するか、後から覆せる形で判断することを提案している。Amazonの株主書簡も、やり直せる決定には軽い手順を使うとしている。[S02][S03]

これを実務に翻訳すると、重要な判断には三つの対処がある。

1. **今決める。** 現在の制約が明確で、比較できるだけの根拠がある。
2. **先に確かめる。** 間違えたときの損失が大きく、短い調査や試作で判断を改善できる。
3. **保留する、または変更範囲を限定する。** 今決める必要がないか、変更を一部分に閉じ込められる。

### 1.3 初期コストは、最初の判断に必要な学習まで含めて小さくする

最初のコード量だけを減らすと、連携確認、運用、利用者の手作業に負担を移してしまうことがある。比較する単位を「最初の利用価値を届け、次の判断ができるまで」に置く。

そのため、最初から自社開発を既定路線にしない。既存サービスをそのまま使う、設定だけ変える、業務のやり方を変える、手作業で価値を確かめる、という選択も残す。GOV.UKのDiscoveryも、課題を調べた結果、開発以外の解決や中止を選ぶことを認めている。[S16]

### 1.4 自前にする価値は、利用者から見て定義する

独自価値は、独自アルゴリズムだけにあるとは限らない。必要な情報のまとまり、仕事の流れ、適切な初期設定、待ち時間、間違いからの回復も候補になる。

自前で作る範囲は、**「既存品を使っても残る、利用者にとって重要な差は何か」**で決める。既存の認証・保存・通知を利用しながら、核心となる体験を自分たちで設計することは十分に可能である。AWSのBuy vs. Build論も、構築する範囲と運用する範囲を別の判断として扱っている。[S19]

## 2. 推奨する進め方の全体像

以下は一方向の工程表ではない。問題、参考調査、全体像は短く往復し、試作で分かったことを前の判断へ戻す。担当者ごとの受け渡し工程にせず、プロダクト・デザイン・実装の視点を同時に使う。一人開発なら、同じ人が視点を切り替える。

各段階の終了条件は、調査や設計を続けすぎないための目安である。重要な前提を確かめる試作は、どの段階でも先に行ってよい。

| 段階 | 主な問い | 最小限残すもの | 次へ進める状態 |
| --- | --- | --- | --- |
| 1. 問題を整理する | 誰が、何を達成できず、今どう対処しているか | 問題・成功条件・制約の短いメモ | 対象と、改善する行動を説明できる |
| 2. 参考・既存品を探す | すでに解けている部分はどこか | 候補の比較と、借りる部分・足りない部分 | 自前で作る理由、または作らずに済む理由がある |
| 3. 全体像を描く | 体験、概念、システムはどうつながるか | 数枚の図と短い説明 | 最初から完了まで辿れ、主要な不明点が見える |
| 4. 重要な判断を詰める | 何が変更困難か。何を誤ると大きく失うか | 判断一覧、必要な試作、重要な決定記録 | 今決めること、試すこと、保留することが分かれる |
| 5. 核となる体験と接続を試す | 使えるか。主要な構成は動くか | 目的を絞ったプロトタイプや小さな実装 | 次の投資判断に必要な証拠が得られる |
| 6. 小さな実用版を提供する | 一つの目的を最後まで達成できるか | 限定した利用範囲、必要な品質、観測・復旧手段 | 対象ユーザーが実際の仕事に使える |
| 7. 観察して改訂する | 何が改善し、何が想定と違ったか | 学習メモ、更新した全体像と次の判断 | 継続・修正・中止の理由を説明できる |

~~~mermaid
flowchart TD
    A["問題・参考・全体像"] --> B{"次の判断は何か"}
    B -->|"変更の負担が大きい・根拠が不足"| C["調査・試作・変更方法の検討"]
    B -->|"根拠が十分、または小さく試せる"| D["限定した実装と提供"]
    B -->|"まだ決めなくてよい"| E["保留条件を記録"]
    C --> B
    D --> F["利用と運用の観察"]
    F --> A
    E -->|"条件が変わる"| B
~~~

**設計の終了条件は、すべてが決まったことではない。** 最初の実用範囲と重大なリスクが分かり、残った不確実性を扱える状態になったら、図や文書の精緻化をいったん止める。

## 3. 問題を整理し、参考と既存の解決策を探す

### 3.1 技術を選ぶ前に、短い問題文を作る

最初のメモでは、以下を答えられればよい。長い事業計画書にする必要はない。

- **誰の、どの場面か。** 「企業の従業員」より「毎週、複数部署からの依頼を振り分ける担当者」のように書く。
- **現在の行動は何か。** 利用しているツール、手作業、代替手段、途中で諦める場面を確認する。
- **何が改善すれば成功か。** 作る機能ではなく、利用者が達成できることや減らしたい負担を書く。
- **なぜ既存の方法では足りないか。** 本当に不足しているのか、使い方を変えれば足りるのかを分ける。
- **今回の制約は何か。** 使える時間、技能、予算、既存データ、連携先、守るべき約束を確認する。

AmazonのWorking Backwardsは、開発前に顧客の経験と重要な疑問を文章にする。小チームでは、この発想を上の短いメモに縮めて使えばよい。文章が整ったことと、需要が確認できたことは別なので、実際の利用者の行動や試用結果も確認する。[S14]

機能要望を受けたら、「その機能があると、どの場面で何ができるようになりますか」と聞き直す。Linearも、要望から利用場面と問題へ立ち戻り、対象ユーザーに合う声を見極めるとしている。[S07]

### 3.2 参考は三つの層で探す

| 探す層 | 見るもの | 持ち帰るもの |
| --- | --- | --- |
| 同じ課題を解く製品・現在の業務 | 利用開始、主要な操作、権限、料金の単位、運用 | 既存の解法と、解けていない部分 |
| 隣接分野の優れた体験 | 大量情報の絞り込み、編集、共有、承認、復旧 | 自分たちの用途にも使える操作パターン |
| 実装できる部品 | 公式SDK、成熟したライブラリ、デザインシステム、管理サービス、スターター | 実際に借りられる機能と採用条件 |

参考の記録は、画像やURLだけで終わらせない。**「どの問題を、どう解いているから参考になるか」**を一文添える。見た目が似ていても、対象ユーザー、頻度、情報量、権限の前提が違えば、そのままは使えない。

ここでの「参考にする」は、考え方や公開されたパターンを学ぶことと、利用条件を確認した部品を再利用することを指す。画面や資産を丸ごと複製する前提ではない。

### 3.3 候補は、重要な利用経路で比較する

汎用的な機能比較表より、代表的な一件を使って比べる。

| 比較する問い | 確認例 |
| --- | --- |
| 主要な仕事が終わるか | 入力から結果確認まで同じケースを通す |
| 調整だけで使えるか | 設定で済むか、継続的な独自改修が必要か |
| 現在の制約に合うか | 権限、データの扱い、連携方式、利用環境 |
| 誰が維持するか | 更新、障害対応、依存する専門知識 |
| 費用の増え方を説明できるか | 利用者数、処理数、保存量が増えた場合 |
| 重要な資産を取り出せるか | レコードだけでなく関連、添付、履歴、権限も確認 |

**調査を止める基準：** 有力な候補と自前案の違い、採否を決める条件、残る重大な不明点を説明できたら、さらに候補数を増やすより試す。調査の前に「何が分かれば判断が変わるか」を書くと、終わりやすい。

### 3.4 課題と解決策を混ぜない

「検索画面を作る」は解決策で、「過去の決定を見つけられない」は課題である。同じ課題には、分類の改善、既存検索の設定、担当者の案内など、複数の解き方がある。

Product TalkのOpportunity Solution Treeは、成果、顧客の未充足ニーズ、解決案、前提の検証を分けて整理する。すべての案件で木の図を作る必要はないが、この区別は参考探索時の思い込みを減らすのに使える。[S17]

**この段階の終了条件：** 「現状より何が良くなるか」と「自前開発が必要な理由」を説明できる。既存品で十分なら、そこで開発を小さくする、または終える。

## 4. 全体像は、体験・概念・システムの三つの視点で描く

構成図だけでは、利用者が何を達成するのかが抜ける。画面だけでは、データの意味や運用上の責任が抜ける。三つの視点を、互いに矛盾しない粗さで揃える。

三つの視点は三冊の設計書を意味しない。小さな案件なら、一つの文書に数枚の図と短い表があればよい。

### 4.1 体験の全体像：開始から結果まで

主要な利用ケースを一つ選び、次を辿る。

1. 利用者は、どのようなきっかけでこの仕組みを必要とするか。
2. 何を持って開始し、最初に何を理解する必要があるか。
3. 何を入力・判断・確認するか。
4. どこで待ち、他の人や外部サービスへ渡るか。
5. 何が起きれば完了し、完了したことをどう知るか。
6. 途中で間違えた、失敗した、離脱した場合にどう再開するか。

オンボーディング、通知、問い合わせ、手作業まで含めて考える。最初からすべてを実装する必要はないが、実装範囲の外にある工程も把握しておく。

主要ケースを端から端まで辿る作業は、Shape Upが説明する、概念の穴や要素間の依存を見つける検討とも対応する。[S05]

### 4.2 概念の全体像：何を扱い、誰が決めるか

まず利用者が使う言葉で整理する。データベースの全カラムやクラス階層は、この段階の必須成果物ではない。

| 項目 | 答える問い | 依頼管理ツールでの例 |
| --- | --- | --- |
| 主要なもの | 利用者は何を作り、探し、変更するか | 依頼、担当者、チーム、対応結果 |
| 関係 | どのものが、どれに属するか | 依頼は一つのチームが管理する |
| 主体と権限 | 誰が閲覧、変更、確定できるか | 依頼者と担当者では変更できる項目が違う |
| 状態 | 何を経て完了するか | 未確認、対応中、完了 |
| 重要な規則 | どの状態でも崩してはいけないことは何か | 閲覧権限のない依頼の本文を返さない |
| 正本 | どこにある情報を正しいものとして扱うか | 対応状況は自分たちのDB、社員情報は既存の名簿 |

ここを曖昧にすると、同じ「完了」が画面・API・分析で別の意味になる。逆に、初期の用語を絶対に変えない前提も不要である。概念を変えたとき、保存済みデータや外部利用者へ何が波及するかを把握する。

### 4.3 システムの全体像：責任と依存を描く

最初は次の二段階で足りることが多い。

- **外側から見る図：** 利用者、自分たちのシステム、連携先を描く。
- **内側を見る図：** アプリ、データの保存先、必要な非同期処理、外部サービスの役割と接続を描く。

C4の公式説明では、すべての詳細レベルを使う必要はなく、多くの開発チームにはシステムコンテキスト図とコンテナ図で十分としている。ここでのコンテナは、アプリやデータストアのような単位で、Dockerの採用を意味しない。またC4は記述の方法であり、開発工程や担当分業を指定するものではない。[S21][S22]

図の箱と線には、次の説明を添える。

- この箱が責任を持つことは何か。
- この線では、どんな情報が、どの向きに流れるか。
- 誰の権限でアクセスするか。
- 相手が使えないとき、どの利用体験が止まるか。
- 自前、既存品、手作業のどれで実現するか。

「フロントエンド」「バックエンド」「DB」と箱を並べただけでは、重要な設計判断は見えにくい。たとえば「依頼の状態はアプリが管理し、外部通知が失敗しても保存結果は失われない」まで説明すると、構成を判断しやすくなる。

### 4.4 品質は、現在の利用場面に結びつけて決める

「高速」「高可用」「拡張可能」だけでは、何を設計すべきか判断できない。利用場面、必要な水準、確認方法を組にする。

| 観点 | 初期に答える問い | 確認方法の例 |
| --- | --- | --- |
| 応答 | どの操作で待ち時間が仕事を妨げるか | 代表的なデータ量・端末・回線で測る |
| データの正しさ | 重複や欠落が起きたら何が困るか | 再送、二重操作、途中失敗を試す |
| 権限 | 誰に何を見せてよいか | 役割・所属・対象の組み合わせを確認する |
| 復旧 | どこまでの停止・データ損失を許容できるか | 保存内容と復旧手順を実際に確かめる |
| 利用可能性 | どの入力方法や支援技術に対応するか | 主要操作をキーボード等で完了させる |
| 費用 | 利用が増えたとき、何が費用を支配するか | 小・中・想定上限の利用量で試算する |

数値が必要な項目は、現状と利用者の必要から決める。一般的なサービス水準を無根拠に持ち込まない。たとえばオフライン利用が現時点で不可欠なら、同期方法は初期の重要な判断になる。将来あり得るだけなら、初期実装の必須条件にはしない。

**この段階の終了条件：** 最初の利用経路、主要なデータと責任、外部依存、今回の範囲、重要な不明点を説明できる。細部の見た目や全機能の一覧が完成するまで待たない。

## 5. 後から変えにくい部分を、どう見分けて詰めるか

### 5.1 変更の難しさは、結びついているものの多さで変わる

「DBは変更困難、UIは変更容易」と固定的に分類しない。利用前のDBは作り直せても、長年使われた画面の用語は、教育、手順書、連携、利用者の習慣に結びついているかもしれない。

本レポートでは、変更の負担を次の四つに分けて確認する。

| 対象 | 変更時に確かめること |
| --- | --- |
| コードと構成 | 何か所に波及するか。新旧の実装が共存できるか |
| 保存済みデータ | 意味、関連、履歴を保って移せるか。失われた情報を再構成できるか |
| 外部への作用 | 送信、公開、課金、外部処理を取り消せるか。訂正や補償が必要か |
| 人と組織への約束 | API利用者、業務手順、契約、学習済みの操作へ何が波及するか |

これは、Amazonの可逆性の考え方、AWSの互換性を保つ変更、Googleの移行費用、Microsoftの段階移行を組み合わせた整理である。[S03][S13][S28][S29]

### 5.2 変更コストと不確実性を分ける

|  | 判断材料が比較的揃っている | 判断材料が不足している |
| --- | --- | --- |
| 変更の負担が小さい | 手早く決めて進む | 小さく試す |
| 変更の負担が大きい | 代替案と影響を確認し、理由を記録して決める | 先に調査・試作する。確定を待てるか、変更を容易にできるかも検討する |

この表だけで優先順位は決めない。追加で三つ問う。

1. **間違えた場合に、誰が何を失うか。** 起こりにくくても損失が大きいものを落とさない。
2. **いつまで決めずにいられるか。** 締切や外部契約があるか。今決める必要は本当にあるか。
3. **今の検証で何が分かるか。** 結果によって選択肢が変わる、実行可能な検証か。

不確実性が高いことだけを理由に、すべてを調査しない。今回使わず、判断を遅らせても困らない機能は保留できる。

### 5.3 初期に確認する価値が高い判断

以下はチェック対象の候補であり、すべてを初日に実装する一覧ではない。

| 判断 | 変更が高くつく理由 | 初期に詰める内容 | 今は保留できる例 |
| --- | --- | --- | --- |
| 主要なデータの意味と所有者 | 記録や集計がその意味に依存する | 代表例、正本、重要な関係、誰が変更できるか | 全将来機能のカラム |
| 組織・利用者・共有の境界 | データが混ざると移行だけで解決しない場合がある | 現在の利用者間で何を隔離・共有するか | 未予定の複雑な権限エンジン |
| 外部に見せるID・API・イベント | 連携先が前提として使い始める | 公開範囲、意味、互換性、変更の伝え方 | 公開予定のない汎用API |
| 保持・削除・履歴 | 記録していない過去や消した情報は戻らない | 今必要な記録、保持目的、削除範囲 | 使途不明の全操作保存 |
| 外部サービスへの依存 | データ、認証、業務が提供元に結びつく | 採用条件、障害時の対応、重要な資産の取り出し方 | すべての提供元に対応する共通基盤 |
| 課金・送信・公開などの作用 | コードを戻しても結果が残る | 対象、実行条件、重複防止、訂正方法 | 未提供の業務の補償機構 |
| プロダクトの基本概念と導線 | 利用者がその使い方を学習する | 主要な言葉、対象、初回から完了までの流れ | 周辺画面の細かな配置 |
| 現在必要な品質・運用 | 構成や保存方法を左右する | 実際に必要な負荷、復旧、利用環境、担当者 | 根拠のない最大規模への対応 |

単一組織だけで使うツールなら、その前提を明記して設計すればよい。実際に複数組織の機密情報を扱うなら、その分離は最初の実用版に必要になる。「将来のため」と「現在の利用を成立させるため」を分ける。

### 5.4 詰め方は、議論だけにしない

判断ごとに、最も安く証拠が得られる方法を選ぶ。

| 不明点 | 小さく確かめる方法 |
| --- | --- |
| 利用者はこの問題を解くために行動するか | 実際の過去の行動を聞く、試用に参加してもらう、手作業で価値を提供する |
| 主要な体験が理解されるか | 代表タスクを、説明を足しすぎずに操作してもらう |
| 外部連携で必要な情報が取得できるか | 実際の権限と代表データで最小の連携を通す |
| 想定する負荷に耐えるか | 負荷を支配する経路だけを測る |
| 採用先から離れられるか | 代表データを取り出し、意味と関連を再現できるか確認する |
| データ形式を変えられるか | 新旧バージョンの読み書きと切替を小さな環境で試す |

SVPGは、価値、使いやすさ、実現可能性、事業としての成立性を異なるリスクとして整理している。技術の試作に成功しても、使われる理由や維持可能性が確かめられたことにはならない。[S15]

### 5.5 変更できる範囲を、設計で増やす

たとえば、保存形式を旧形式Aから新形式Bへ変えるとする。AとBは同じ情報を表し、新旧の版で読み書きしても必要な情報や意味が失われないことを前提とする。実際の検証では、読み取りだけでなく更新・再保存まで確認する。

| 版 | 読める形式 | 書く形式 | 直前の版へ戻すときの条件 |
| --- | --- | --- | --- |
| V1 | A | A | 変更前 |
| V2 | AとB | A | Bを書いていなければV1へ戻せる |
| V3 | AとB | B | Bも読めるV2へ戻せる |

この例では、**Bを書き始めた後、そのままV1へ安全に戻すことはできない**。V3を入れる前には、必要な読み手がすべてV2相当になったことも確認する。旧形式Aの読み取りを削るときは、Aのデータが残らず、巻き戻し先や残存する処理もAを再び書かないことを確認する。この削除は別の変更として扱う。AWSは、このように変更を段階に分けて巻き戻し可能な範囲を作る方法を説明している。[S28]

日常的な設計でも、「切り替えられる境界」「保存済みデータの扱い」「戻せる地点」を先に考えるとよい。ただし、将来のあらゆる変更を可能にする仕組みまで作る必要はない。

### 5.6 決定を保留するときも、再開条件を置く

保留は放置とは違う。たとえば「高度な検索は、現在の検索で目的の情報を見つけられない具体例が繰り返し現れたら再検討する」と書く。

重要な決定はADR（設計上の決定記録）に残す。Nygardの原案は文脈、決定、状態、結果を短く記録し、変更された判断も履歴として保持する。本レポートでは、さらに「見直す条件」と「変更時の手順」を加えることを勧める。[S25]

**この段階の終了条件：** 今回の利用で重大な損失につながる不明点を扱い、決定・実験・保留を分けられたら先へ進む。残りを調べても選択が変わらないなら、調査量を増やすより限定した実用へ移る。

## 6. 既存品を使い、自前の開発を価値の核に集中する

### 6.1 まず、開発量の少ない選択肢から試す

| 選択 | 向いている状況 | 主に確認すること |
| --- | --- | --- |
| 開発せず、業務や情報提供を変える | 問題が手順や情報不足にある | 利用者の負担が実際に減るか |
| 既存製品をそのまま、または設定して使う | 主要な用途が既存の流れに収まる | 必須条件と運用が合うか |
| 既存サービス・ライブラリを組み合わせる | 部品は揃っているが、一連の体験が足りない | 統合費用と責任の境界 |
| 足りない部分を自前で作る | 重要な体験や判断を既存品では実現できない | 持ち続ける価値と保守能力があるか |

この順番は、自前を否定するためではなく、最も小さい投資で成立する解を見つけるための探索順序である。

Fowlerは、競争上の差が生まれる機能と、確実に動けばよい共通機能を区別している。共通機能を購入した後に大幅に改造すると、既製品を使う利点を失いやすいという指摘もある。[S18]

### 6.2 「ここだけは自前にする」を説明する

自前にする候補は、次の二つの問いで絞る。

- ここを自分たちで制御できると、対象ユーザーの成果が具体的に良くなるか。
- その制御を持ち続ける価値が、実装・維持・運用の負担を上回る見通しがあるか。

たとえば依頼管理なら、認証方式を独自に作ることより、「必要情報が揃った依頼を、適切な担当者へ、迷わず渡せること」に価値があるかもしれない。ただし、これは事業次第である。認証そのものを売る製品なら、同じ分類にはならない。

既存品をつなぐ設計にも独自価値はある。利用者に複数のアカウント、画面、用語の往復を強いてしまう場合、その負担も含めて採否を考える。

### 6.3 初期費用と、その後の費用を別々に見る

見積もりは、一つの合計点に圧縮しすぎない。

| 費用 | 含めるもの |
| --- | --- |
| 最初に使えるまで | 調査、実装、設定、データ投入、連携、導入説明 |
| 使い続けるため | 利用料金、更新、障害対応、問い合わせ、担当者の学習 |
| 変えるため | データ移行、コード修正、並行運用、利用者の再設定 |
| 他の仕事を遅らせる分 | 核心の検証や顧客対応に使えなくなる時間 |

初期の利用量と、成立した場合の利用量を分けて比較する。未知の利用量を精密に当てようとせず、「この条件を超えると選択が変わる」という境目を調べる。

クラウドやSaaSの採用は、運用をすべてなくすことではない。設定、権限、データ、業務結果、利用者への説明のどこを自分たちが担うかを決める。提供元の記事は参考になるが、そのサービスを選ぶ商業上の立場も踏まえて読む。[S19]

### 6.4 依存を許容しつつ、失いたくない資産を守る

「ロックインをゼロにする」を初期目標にすると、利用できる便利な機能まで捨てたり、未使用の共通基盤を作ったりしやすい。重要なのは、依存の内容と代償を理解して採用することである。

確認する資産は、業務データ、添付、履歴、権限、外部ID、ログイン方法、連携先の設定など。すべてを同じ深さで調べず、失うと困るものに絞る。

**エクスポートできるだけでは、移行できるとは限らない。** データ間の関連や意味を復元できるか、移行先に取り込めるか、利用者の再設定が必要かまで見通す。重要な依存では、代表データを一度取り出して確認する価値がある。

一方、移行先が未定なら、完全な移行ツールまで先に作らない。「この負担なら今は受け入れる」という決定も合理的である。

**この段階の終了条件：** 自前で持つ価値、採用先の責任、最初の費用、主要な依存とその代償が説明できる。すべてを交換可能にする必要はない。

## 7. 変更しやすい構成を、少ない仕組みで作る

### 7.1 小規模な新規Web開発では、配備構成を単純にする

最初の候補としては、チームが扱える技術で作る単一アプリと、必要な少数の管理サービスを検討する。内部は責任に応じて分ける。

FowlerのMonolith Firstは、初期にはサービス境界を見極めにくく、複数サービスの管理が追加費用になると説明している。ただし、著者自身が限られた事例に基づく助言としており、すべての新規開発に対する規則ではない。[S23]

初期から分ける理由がある場合もある。独立した障害隔離、明確に異なる負荷、既知の責任境界、別々の配備制約などである。逆に、単一アプリだから自動的に変更しやすくなるわけでもない。データや処理が無秩序に結びつけば変更は難しくなる。

### 7.2 モジュールの境界は、閉じ込めたい変更から考える

Parnasの情報隠蔽の考え方は、難しい、または変わりそうな設計判断を他の部分から隠す単位で分けるというものだ。モジュールを増やすこと自体が目的ではない。[S20]

各境界について、次の説明ができるか確認する。

| 検討する変更 | 境界を設ける意味 |
| --- | --- |
| 通知の提供元を変える | 業務処理が、提供元固有の入力形式に直接依存しないようにする |
| 料金のルールを変える | 計算の意味を、画面や外部APIの詳細と混在させない |
| 検索方式を変える | 検索対象と結果の意味を、特定の検索製品の都合だけで決めない |
| 画面の構成を変える | 業務上の規則を、特定の画面操作だけに埋め込まない |

これらは境界の候補であり、すべてに大きなインターフェース層を設ける推奨ではない。提供元への呼び出しを少数の箇所に集めるだけで十分な場合もある。

### 7.3 将来の自由度のために、現在の理解を難しくしない

次の仕組みは、現在の要求があるときに採用する。

- 任意のワークフローを作れる汎用エンジン。
- 複数クラウドで動くための独自抽象化。
- あらゆるDBを交換可能にする共通層。
- 将来のサービス分割だけを目的とするイベント基盤。
- 一度しか現れない処理のためのプラグイン機構。

FowlerのYAGNIは、未確定の将来機能の先回りを避ける一方、リファクタリングやテストなど、変更しやすさを支える活動を否定しない。[S24]

GoogleのSRE資料も、部品が汎用的で単純でも、その利用側に意味や互換性の負担を押しつけると、全体は複雑になる事例を示している。[S13]

判断に迷ったら、**「具体的にどんな変更が起き、そのとき何を直すか」**を一度想像する。その修正が十分小さいなら、抽象化を今作る必要は薄い。

### 7.4 最小限の土台は、現在の変更と利用を守るものに絞る

| 土台 | 目的 | 初期の範囲 |
| --- | --- | --- |
| 変更履歴と再現できるビルド | 動いている版と変更点を追える | ソース、依存、必要な設定を追跡する |
| 重要な規則の検証 | 変更で壊れると困ることを発見する | 権限、金額、状態遷移、重要なデータ処理など |
| 主要な経路の確認 | 接続して初めて出る問題を見つける | 代表的な一連の操作と失敗ケース |
| 配備と停止・復旧の手順 | 小さな修正を届け、問題に対処する | 現在の構成に合う簡単な方法 |
| 保存データの変更手順 | 意味や関係を保って更新する | 今回の変更に必要な移行と検証 |
| 運用上の観測 | 失敗が起きた場所と影響を知る | 主要操作の結果、エラー、処理状況 |

テスト項目や運用ツールを一律に増やす必要はない。壊れると困る規則と、これから変更する境界に集中する。試作用の使い捨てコードと、本番データを扱う実装では、必要な水準を分ける。

### 7.5 変更しやすさは、具体的な変更で確かめる

代表的な変更を一つ考え、どこに波及するかを確認する。「依頼の必須項目を変える」「通知の提供元を変える」「一つの状態を追加する」などでよい。

変更する箇所の数だけでなく、判断に必要な知識、データの移行、利用者への影響まで見る。ソースが数行変わるだけでも、外部の契約を壊すなら軽い変更ではない。

MicrosoftのStrangler Figは、稼働中の仕組みを部分ごとに置き換える方法を説明している。0から作る段階で移行基盤一式を導入する必要はないが、責任や依存が明確であるほど、後の置き換えを検討しやすい。[S29]

## 8. UXのよいプロダクトから、何を借りるか

### 8.1 見た目だけでなく、利用者が迷わない仕組みを見る

GitHubのPrimerは、一貫した用語や慣れたパターンによって、利用者がUIの解読より仕事に集中できることを重視する。アクセシビリティも、設計と動作に影響するため、初期から考えるとしている。[S10]

参考プロダクトを触るときは、次を見る。

| 観点 | 観察すること |
| --- | --- |
| 現在地 | 何を見ていて、どの対象に操作するのか分かるか |
| 次の行動 | 最も重要な操作を迷わず選べるか |
| 初回利用 | 空の状態で、何から始めるか分かるか |
| 編集と保存 | 何が保存済みで、何が未保存か分かるか |
| 待ち時間 | 操作を受け付けたことと、処理の状況が伝わるか |
| エラー | 何が失敗し、どう続ければよいか分かるか |
| 回復 | 誤操作を取り消す、再実行する、途中から戻る手段があるか |
| 習熟 | 初心者が始められ、繰り返し使う人も効率よく扱えるか |

この観察は、余白や色だけを模倣するより、自分たちの体験に転用しやすい。Primerの全構成を採用する必要はなく、対象ユーザーの仕事に合うパターンを選ぶ。

### 8.2 内部の変更容易性と、利用者向けの自由度を分ける

Linearは、目的に沿った設計、分かりやすい言葉、余分な管理作業の削減、単純に始められることを重視する。[S09]

この考え方から、本レポートでは次を勧める。

- 開発側は、判断を見直せる構造にする。
- 利用者には、最初から分かる標準の使い方を用意する。
- 設定項目は、実際に異なる必要が確認されたところから増やす。

「後から自分たちが変えたい」を、すべて利用者の設定項目に変換しない。設定項目は、説明、選択、組み合わせ確認、サポートの仕事も増やす。

### 8.3 範囲を狭くして、選んだ体験を成立させる

初回提供で守りたいのは、一つの目的を最後まで果たせることだ。

たとえば検索だけを提供するなら、「検索結果が出る」だけでなく、該当なし、読み込み、権限不足、失敗、再試行を、その用途に必要な範囲で扱う。一方で、まだ必要のない高度な絞り込みや大量の表示形式は保留できる。

Linearは、初期プロジェクトを小さくし、利用者から短い周期で学ぶことを勧めている。同社が示す人数や週数をそのまま採用する必要はない。本レポートではこの実践を、全体の構想を持ちながら、最初の提供範囲を限定する進め方に取り入れる。[S08]

### 8.4 大枠のレビューと細部のレビューを分ける

| レビュー | 確かめること | 使う材料 |
| --- | --- | --- |
| 問題と方向 | 解く課題、対象、選択した解き方が妥当か | 問題文、観察事実、参考比較 |
| 構成と体験 | 情報のまとまり、主要な流れ、責任がつながっているか | 粗い図、代表ケース |
| 操作の細部 | 入力、保存、待ち、失敗、回復が分かるか | 操作可能な試作、実装 |
| 実用 | 実際の仕事を、必要な品質で終えられるか | 実データに近いケース、利用観察 |

レビューの依頼には、「今回は導線と情報のまとまりを見たい」のように焦点を書く。Linearのように大枠と細部への意見を分けると、方向性の議論中に細かな見た目へ話が流れるのを防ぎやすい。[S06]

## 9. 小さな実装・公開・学習で設計を育てる

### 9.1 試作、構成の検証、実用版を区別する

| 種類 | 主に確かめること | それだけでは分からないこと |
| --- | --- | --- |
| 体験のプロトタイプ | 用語、理解、導線、操作 | 本番の性能、データの正しさ、運用 |
| 特定の技術検証 | 連携、負荷、移行など一つの前提 | 全体の使いやすさや需要 |
| Walking Skeleton | 主要な構成要素と配備経路がつながること | 利用価値が十分か |
| 限定した実用版 | 実際の利用で価値が出ること | より広い利用者や負荷への適合 |

Walking Skeletonは、主要な構成を端から端までつなぐ最小の動作する実装である。たとえば「入力、処理、保存、結果表示、配備」の細い経路を通す。構成図の前提を早く確かめるために使い、これが動いたことを価値の検証と取り違えない。[S27]

試作には、確認したい問い、使うデータ、終了条件、結果を受けた次の判断を置く。見栄えを磨くことや、試作コードをすべて本番へ残すことを目的にしない。

### 9.2 提供する価値と、コード変更の単位を分ける

利用者に届ける単位は、「依頼を登録し、担当者が確認し、結果を知る」のような一連の目的で考える。その内部のコード変更は、レビューできる小さな単位に分ける。

GoogleのSmall CLsは、一つの意味を持ち、理解に必要な情報が揃い、取り込んだ後も正常に動く変更を勧める。小ささは行数だけでは決まらない。[S12]

DORAも小さな変更によるフィードバックを重視し、開発を細分化しても、後でまとめてテスト・公開すると学習が遅れる点を挙げる。[S26]

したがって、「まず全DB、その後すべてのAPI、最後に全画面」のように長期間結合しない進め方は、今回の価値観とは合いにくい。内部の実装順には依存があっても、早い時点で一つの利用経路を通す。

### 9.3 配備、公開、データ変更を別々に考える

GitHubはfeature flagsで、コードの配備と、誰に機能を見せるかを分け、段階的に公開する実践を紹介している。一方で、残った分岐やテストの保守負担も説明している。[S11]

小チームでは、必要に応じて既存の機能や簡単な設定で実現すればよい。大規模なフラグ基盤を自作する必要はない。

フラグを使うなら、公開対象、担当者、停止条件、役割を終えた後の削除条件を決める。そして、**機能を無効にすることと、すでに生じた結果を戻すことを分ける。** 送信した通知や変更済みデータは、別の対応が必要になる。

### 9.4 学ぶ対象を、実装前に決める

| 見る対象 | 問い | 観察例 |
| --- | --- | --- |
| 利用者の成果 | 目的を以前より達成しやすいか | 完了までの時間、やり直し、手作業の減少 |
| 継続する理由 | 次の機会にも使うか | 実際の再利用、元の方法に戻る場面 |
| 守る品質 | 価値を損なう失敗は起きていないか | エラー、欠落、誤った権限、問い合わせ |
| 変更の負担 | 修正して確かめるまでが重くなっていないか | レビュー待ち、配備待ち、変更の波及範囲 |
| 維持する費用 | 利用増加に合わせて支えられるか | 処理当たりの費用、運用の手作業 |

初期ユーザーが少ないときは、無理にA/Bテストで結論を出そうとせず、代表タスクの観察や、実際に使い続けた理由・やめた理由を集める。発言だけでなく行動を見る。初期の利用者が全市場を代表しているとも考えない。

### 9.5 観察結果を、全体像へ戻す

各回の区切りでは、次だけを確認すればよい。

1. 何を確かめるつもりだったか。
2. 何が観察され、どの前提が変わったか。
3. 全体像、範囲、重要な決定のどれを直すか。
4. 次に、何を作る・調べる・やめるか。

要望が来るたびに追加するのではなく、最初に決めた対象と成果に照らす。使われなかった仕組み、役割を終えたフラグ、重複した処理を減らすことも、次の変更を軽くする仕事に含める。

## 10. 一つの案件を通して考える

以下は説明用の架空例であり、実在する企業の調査結果ではない。

### 10.1 出発点

小規模な開発チームに、社内から依頼が届く。依頼の情報が足りず、何度も聞き返す。担当者が分からず、受け付けられたかを依頼者が確認し直している。

ここでの目標は「新しい課題管理システムを作る」ではなく、**必要な情報が揃った依頼を、適切な担当者へ渡し、依頼者が受付結果を分かるようにすること**とする。

### 10.2 参考と既存品を調べる

現在の課題管理サービス、フォーム、社内ポータルで、この流れを作れないかを試す。単に機能名が存在するかを見るのではなく、実際に届いた依頼の例を一件通す。

既存製品の設定だけで必要な改善が得られるなら、それを採用して終了する。ここでは仮に、依頼の種類ごとに必要な情報が異なり、依頼者が迷わず入力できる案内だけが不足したと分かったものとする。

その場合は、受付の体験を自前にする案を検討する。既存の課題管理、社員認証、通知を全面的に作り直す理由はない。

### 10.3 全体像を揃える

| 視点 | 最初に描くこと |
| --- | --- |
| 体験 | 依頼の種類を選ぶ → 必要な情報を入力する → 送信する → 受付結果と担当を確認する |
| 概念 | 依頼、依頼者、受付担当、担当チーム、受付状態 |
| システム | 受付アプリ、依頼の保存先、既存の本人確認、既存の通知、担当者の作業場所 |
| 範囲 | 受付と引継ぎまで。開発計画や工数管理は今回の対象外 |

実装前に、この流れを粗い試作で確認する。どの項目が必要かは、過去の依頼と受付担当者の実際の判断から決める。

### 10.4 変更が高くつく部分を先に扱う

| 判断 | 初期の扱い |
| --- | --- |
| 誰が依頼を閲覧できるか | 部署全体へ見せてよいか、依頼者と担当だけかを確認する |
| 受付状態の意味 | 「送信済み」「受理済み」「担当へ引継ぎ済み」の違いを必要な範囲で定める |
| どこが正本か | 受付情報をどこで確定し、外部の記録とどう対応させるか決める |
| 通知失敗の扱い | 依頼の保存と通知の成否を分け、失敗を把握して再対応できるようにする |
| 将来の多組織対応 | 現在は一組織という前提を記録し、汎用的な仕組みは作らない |
| 画面の細かな配置 | 操作試験で変えられるため、初期に凍結しない |

外部サービスへの自動連携が今回の価値に不可欠なら、必要な権限と代表データで先に通す。自動化が不可欠でなければ、限定した試用では受付担当者の手動引継ぎも候補になる。手作業の量を記録し、継続できない負担になったら自動化を判断する。

### 10.5 何を借り、何を作るか

| 領域 | 方針 |
| --- | --- |
| 本人確認 | 組織で利用できる既存方式を調査する |
| フォーム部品、表示、基本操作 | 適合する既存のUI部品を使う |
| 依頼種類ごとの案内と必要情報 | 独自価値の候補として設計する |
| 保存、配備、通知の基盤 | 現在の条件に合う既存の仕組みを使う |
| 担当者の作業管理 | 既存の業務を活かし、受付とのつながりだけを整える |
| 汎用ワークフロー、高度な分析 | 今回の必要性が確認できるまで保留する |

既存の認証やUI部品を採用しても、アクセス制御や一連の操作が正しくなるかは、受付アプリ全体で確認する。

### 10.6 最初の実用範囲を決める

まず一種類の依頼、一つの担当チームに限定する。その条件の中では、入力、保存、受付結果、引継ぎまで成立させる。失敗時に依頼が消えたのか、保存されたのか分からない状態は避ける。

試用では、次を観察する。

- 受付時の聞き返しは減ったか。
- 依頼者が途中で迷う項目は何か。
- 担当が決まるまでにどこで止まるか。
- 元の連絡手段へ戻る理由は何か。
- 受付担当者に新しい手作業が増えていないか。

改善が確認できれば、依頼の種類や担当チームを増やす。問題が残るなら、入力、分類、担当の決め方のどこを変えるべきかを判断する。

この例では、全体像を先に描いているが、全体の機能を初回に作ってはいない。変更が高くつく意味や権限を先に確認し、変更しやすい入力の細部は実際の観察で調整している。

## 11. 着手時の進め方と、チームでの運用

### 11.1 最初の5作業日の配分例

次は、利用者に接触でき、外部制約が比較的少ない小規模案件の例である。5日で製品を完成させる計画ではなく、次に何へ投資するかを決めるための配分として読む。

| 目安 | 主な活動 | その日の判断材料 |
| --- | --- | --- |
| 1日目 | 現在の利用場面を聞く。現状、参考、既存品を確認する | 問題、代替手段、成功条件の仮説 |
| 2日目 | 候補を実際のケースで比べ、全体の流れと構成を描く | 借りる部分、自前候補、主要な不明点 |
| 3日目 | 重要なリスクを一つか二つ検証する | 採用・変更・保留を選べる結果 |
| 4日目 | 核となる操作、または主要な接続を試す | 体験か技術の、最も必要だった証拠 |
| 5日目 | 結果を見直し、最初の実用範囲を決める | 小さな実装計画、重要な決定、まだ決めないこと |

何を試すかは最も大きい不確実性で変える。価値が不明なら利用者との検証を増やし、技術が成立するか不明なら早く接続や性能を試す。日程に合わせて不明点を隠さない。

### 11.2 会議の数より、決定と実物のつながりを保つ

最初からScrumやShape Upの運用全体を採用する必要はない。既存の課題管理とリポジトリで、次をつなぐ。

- プロジェクトには、目的、初回範囲、成功条件を置く。
- 調査や試作のタスクには、確かめる問いと終了条件を置く。
- 実装タスクには、支える利用場面と完了条件を置く。
- 重要な判断には、理由と見直す条件をリンクする。
- 区切りでは、タスク数より実物と観察結果を確認する。

作業の途中で重要な前提が崩れたら、次の定例会議を待たずに相談する。一方、変更が容易な細部まで毎回全員の承認を求めない。担当範囲と、共有が必要な判断を分ける。

### 11.3 状況によって、深く考える場所を変える

| 状況 | 比重を増やすところ |
| --- | --- |
| 価値がまだ不明な新規製品 | 現在の行動、代替手段、実際の試用 |
| 現場をよく知る小さな業務ツール | 既存品との適合、最短の実用経路、運用負担 |
| 複数組織に提供するSaaS | データと権限の境界、導入・退出、利用量による費用 |
| 公開APIや外部連携が主な製品 | 契約、互換性、バージョンの共存、障害時の影響 |
| オフラインや端末特性が中心 | 同期、配布済みの版、利用環境、データの競合 |
| 規制・安全・大規模移行の制約がある | 必要な証跡、検証、移行・復旧、専門家との確認 |

**共通の判断基準は、現在の対象と約束を成立させるために必要かどうか。** 適用しない要件も明示し、将来の可能性だけで初期範囲を膨らませない。

## 13. 異なる知見を、どう組み合わせたか

資料をそのまま足し合わせると、手順も文書も増える。ここでは、各知見が解こうとしている問題を切り分けた。

| 張り合う考え方 | このレポートでの組み合わせ |
| --- | --- |
| 大枠を先に考える / 実装から学ぶ | 全体像は依存と不明点を見つけるために描き、実装で更新する |
| 変更困難な部分を詰める / 判断を遅らせる | 検討は早く始め、確定の時期は証拠・締切・変更費用で決める |
| 構築費用を減らす / 変更しやすさを守る | 未確定の機能を減らし、現在の安全な変更に必要な土台へ投資する |
| 既存品を使う / 独自価値を出す | 部品と運用を借り、利用者の成果を左右する体験や判断を制御する |
| 範囲を決める / 顧客から学ぶ | 今回の投資枠は決め、観察結果によって中身・次回・継続判断を変える |
| 小さく出す / UXをよくする | 利用場面を狭め、その範囲で開始・完了・回復を成立させる |
| 将来交換できるようにする / 抽象化を増やさない | 影響が大きい依存だけを整理し、移行が必要になるまで仕組みを増やさない |

Shape Upの時間枠や組織運営、Linearのチーム規模、Amazonの意思決定手順、GoogleやGitHubの運用基盤は、それぞれの文脈にある。本レポートでは、構想の整え方、リスクの扱い方、変更の小ささ、利用者の体験といった判断の考え方を取り入れた。[S03][S04][S08][S11][S12]

### 設計中に戻ってくる七つの問い

1. **何が良くなるのか。** 作るものの説明ではなく、利用者の成果を説明できるか。
2. **すでに使えるものは何か。** 開発せずに済む案を実際に比較したか。
3. **全体はつながっているか。** 開始から完了まで、担当とデータの流れを辿れるか。
4. **何を誤ると大きく失うか。** コード以外のデータ、外部作用、約束も見たか。
5. **何を先に試せば判断が変わるか。** 検証の終了条件と次の行動があるか。
6. **今回はどこまでで価値が出るか。** 一つの目的を狭い範囲で完了できるか。
7. **次に変えるとき、何が必要か。** 選択の理由、見直し条件、変更の見通しが残っているか。

この七つに答えられる状態を作り、実際の利用で答えを更新していくことを、設計の継続的な仕事にする。

## 14. 出典と、さらに読む順序

### 14.1 調査の範囲

原論文、提唱者の著作、企業・公的組織の公式文書から、変更容易性、初期投資、既存品の利用、主要な体験の設計に関係する資料を選び、本文を確認した。網羅的な文献レビューや製品ランキングではなく、今回の価値観に沿った実践の比較・統合である。

### 14.2 最初に読むなら

- **大枠をどこまで詰めるか：** Shape Upの[S04]と[S05]。
- **問題から設計へ進む具体的な感覚：** Linearの[S06]。
- **アジャイルと事前設計をどう両立するか：** Fowlerの[S02]。
- **どこを自前にするか：** Fowlerの[S18]とAWSの[S19]。
- **変更可能性を実装へ落とすには：** Parnasの[S20]、ADRの[S25]、AWSの[S28]。

### 14.3 出典一覧

- **[S01] Agile Manifesto署名者 — Principles behind the Agile Manifesto**。2001年。採用した論点：変更への対応、良い設計、単純さ。

- **[S02] Martin Fowler — Is Design Dead?**。2004年5月版、初稿2000年。採用した論点：短い事前設計、進化的設計、可逆性。

- **[S03] Jeff Bezos / Amazon — 2016 Letter to Shareholders**。2016年度書簡、2017年公表。採用した論点：可逆な決定に応じて手順を軽くすること。

- **[S04] Ryan Singer / Basecamp — Shape Up: Principles of Shaping**。ページに日付記載なし。採用した論点：主要な要素と接続を考え、細部と範囲を適切に扱うこと。

- **[S05] Ryan Singer / Basecamp — Shape Up: Risks and Rabbit Holes**。ページに日付記載なし。採用した論点：利用ケースを辿り、重要な未知や依存を先に確認すること。

- **[S06] Linear — Manage design projects**。日付記載なし。採用した論点：問題確認、探索、大枠と細部のレビュー、設計と実装の協働。

- **[S07] Linear — Build with users**。日付記載なし。採用した論点：機能要望から利用場面へ立ち戻り、対象ユーザーから学ぶこと。

- **[S08] Linear — Scope projects down**。日付記載なし。採用した論点：初期の範囲を小さくし、早い提供から学ぶこと。

- **[S09] Linear — Principles & Practices**。日付記載なし。採用した論点：用途に沿った設計、明確な言葉、余分な管理作業の削減。

- **[S10] GitHub / Primer — Getting started**。日付記載なし。採用した論点：一貫した体験、慣れたパターン、初期からのアクセシビリティ。

- **[S11] Alberto Gimeno / GitHub — How we ship code faster and safer with feature flags**。2021年4月27日。採用した論点：配備と公開の分離、段階公開、フラグの維持負担。

- **[S12] Google Engineering Practices — Small CLs**。日付記載なし。採用した論点：意味のまとまった小さな変更と、理解・レビュー・修正のしやすさ。

- **[S13] Google SRE — The Site Reliability Workbook, Chapter 7: Simplicity**。公式公開章、ページに公開日記載なし。採用した論点：システム全体の単純さ、移行・並行運用を含めた費用。

- **[S14] AWS Executive Insights — The Secrets to AWS Product Management**。日付記載なし。採用した論点：Working Backwards、PR・FAQ、顧客の経験と仮説検証。

- **[S15] Marty Cagan / SVPG — The Four Big Risks**。2017年12月4日。採用した論点：価値、使いやすさ、実現可能性、事業としての成立性。

- **[S16] GOV.UK Service Manual — How the discovery phase works**。2016年8月4日公開、2021年6月21日更新。採用した論点：問題・制約・代替手段の調査と、開発しない判断。

- **[S17] Teresa Torres / Product Talk — Opportunity Solution Trees: Visualize Your Discovery to Stay Aligned and Drive Outcomes**。2023年12月6日。採用した論点：成果、ニーズ、解決案、前提の検証を区別すること。

- **[S18] Martin Fowler — Utility Vs Strategic Dichotomy**。2010年7月29日。採用した論点：差別化する機能と共通機能を区別し、投資を変えること。

- **[S19] Gregor Hohpe / AWS — Buy vs. Build Revisited, Part 4: You Might Be Asking the Wrong Question**。2021年2月17日。採用した論点：どこまで作るかと、何を運用するかを別々に判断すること。

- **[S20] D. L. Parnas — On the Criteria To Be Used in Decomposing Systems into Modules**。Communications of the ACM 15(12), 1053–1058, 1972年12月。採用した論点：変わり得る設計判断をモジュールで隠すこと。

- **[S21] Simon Brown / C4 model — Diagrams**。日付記載なし。採用した論点：役立つ抽象度を選んでシステムを記述すること。

- **[S22] Simon Brown / C4 model — Frequently asked questions**。日付記載なし。採用した論点：C4は開発工程や組織分業を指定するものではないという説明。

- **[S23] Martin Fowler — Monolith First**。2015年6月3日。採用した論点：境界が未確定な初期段階での、単純な配備構成の利点と条件。

- **[S24] Martin Fowler — Yagni**。2015年5月26日。採用した論点：将来機能の先回りと、現在の変更容易性への投資の区別。

- **[S25] Michael Nygard / Cognitect — Documenting Architecture Decisions**。2011年11月15日。採用した論点：重要な決定の文脈、理由、状態、結果を短く記録すること。

- **[S26] DORA / Google Cloud — Working in small batches**。2025年12月8日更新。採用した論点：小さな変更と、テスト・公開までを含めたフィードバック。

- **[S27] Clint Shank / O’Reilly — Start with a Walking Skeleton, 97 Things Every Software Architect Should Know, Chapter 60**。2009年、出版社公開の抜粋。採用した論点：主要な構成を最小の実動経路で検証すること。

- **[S28] Sandeep Pokkunuri / Amazon Builders’ Library、現AWS Builder Center — Ensuring rollback safety during deployments**。2019年12月5日。採用した論点：新旧の互換性、段階的な変更、戻せる地点の確認。

- **[S29] Microsoft Azure Architecture Center — Strangler Fig pattern**。2026年6月2日更新。採用した論点：段階的な置き換え、その適用条件、移行完了後の巻き戻し費用。
