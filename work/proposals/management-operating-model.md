# hns 開発のマネジメント・オペレーティングモデル（案）

2026-11-16 / 採用（D067・D068・D069）。対象は hns の開発（人間1人 + 複数 agent）。
背景の調査は [AI時代のプロダクトマネジメント](../research/ai_era_product_management.md)。

> **結論：いまの開発運用は、調査でいう「ハーネス」の guide / guardrail / sensor がすでに強い。足すのは3層だけ。成果の層（テーゼと Moat）、完了の層（証拠）、蓄積の層（判断の蒸留）。プロセスは増やさず、既存の器に欄を足す。**

## 1. 既にあるもの（強み）

| 機制 | 根拠 | なぜ効くか |
| --- | --- | --- |
| 変更レーンは最大3本、統合は直列 | [D060](../../docs/decisions/D060.md) / [parallel-change.md](../../docs/parallel-change.md) | WIP を制限し、Little's law の W を守る |
| touches 契約と依存 DAG | [work/README.md](../README.md) | 意味的な競合と先回りを防ぐ |
| 著者とレビュアーの分離 | [review.md](../../docs/review.md) | 自分の読みをレビューと呼ばない |
| 小さな変更（100行目安・2日上限） | D060 | レビューの認知負荷を上げない |
| 関門（gate・anti-slop・path 別不変条件） | [AGENTS.md](../../AGENTS.md) | 機械で判定できるものを人間に戻さない |
| 判断ログ（代替案と無効条件つき） | [decisions.md](../../docs/decisions.md) | 判断を再利用できる |
| 着手規律（now のみ、agent は昇格しない） | [D054](../../docs/decisions/D054.md) | 優先度の判断を人の側に残す |

研究の言葉に直すと、guide（AGENTS.md / docs）、guardrail（gate / touches / レーン上限）、sensor（review / 計測）が揃っている。Mercari の「機構は外から買えるが、判断基準は自前で持つしかない」に近い状態だ。**この土台を壊さずに、3つの層を足す。**

## 2. 足りない3つ

### 2.1 成果の層がない

いまの計測はフロー（リードタイム、レビュー待ち、統合待ち、競合、ゲート時間、統合後の失敗）だ。これは「速く安全に流れているか」を測るが、**ユーザーに何が起きたか**は測っていない。

DORA 2025 は、ユーザー中心性が欠けた状態で AI を使うとチーム性能に**負の影響**が出ると報告している。ゲートが緑でレーンが回るほど、成果が出ていないことに気づきにくくなる。Cagan の言う「予測可能性と成果のトレードオフ」が、そのまま当てはまる。

### 2.2 完了が L3 で止まる

いまの完了は「review PASS + npm run check + rebase + 統合 + 統合後の確認」で、Done ladder の **L3（統合され、動く）** に当たる。L4（成果が観測された）と L5（学習が蓄積された）がない。

issue の Result は書かれている。ただし verdict / reviewer / HEAD / blocking 指摘が中心で、**レビューで使われず、進捗にも次回の判断にも使われていない**。Intent・Limits・Invalidation がないうえ、読む側の形式もない。「何のために作り、何を保証し、何が変わったら完了を取り消すか」が残らない。Proof of Done の言う「証拠を伴う変更」に、あと1枚足りない。

### 2.3 判断が蓄積されない

レビューの指摘はその場で直して閉じる。同じ指摘が別の issue で再発しても、ルール・テスト・eval に蒸留されない。Pydantic は 4,668 件のレビューコメントから 150 ルールの AGENTS.md を作ったが、hns はその逆をやっている。

decisions は質が高い。ただし「次の判断を速くする」ための導線がない。判断リードタイムを測っていないので、改善もできない。

そして、効率化で浮いた時間の再投資先が決まっていない。LayerX の松本が言う通り、**効率化そのものは競争優位ではない**。浮いた時間を plan の機能追加に全部戻すと、差は縮まらない。

## 3. 追加する運用（最小）

### 3.1 四半期：テーゼと Moat 台帳（1枚）

work/THESIS.md を四半期に1枚だけ更新する。項目は WHO / WHAT / WHY US / ACCUMULATES / NOT。加えて Moat 台帳を4行。

| Moat 候補 | 今期に増えた証拠 | 投下した時間 | 次の一手 |
| --- | --- | --- | --- |
| 長期ループ（記録→判断→次の意図） | 例：レコードを持つ issue が N 件、次の判断に使われた件数 | 例：週2時間 | 例：0116 に criteria を足す |
| 再開可能性（複数マシン） | 例：2台目で restore が通った | 例：E レーン1本 | 例：0148 の後に実測 |

最後にストレステストを1問。「この戦略を反対にしても、馬鹿げていないか」。誰も反対しない標語は戦略ではない。

### 3.2 記録を構造化し、消費者を決める

**Result に欄を足す案は採らない。** Result はすでに書かれているが、レビューで使われず、進捗にも次回の判断にも使われていない。問題は欄の不足ではなく、**読む側と形式**がないことだ。

1 issue 1 レコードを正とする。形式は YAML（例: work/records/0195.yaml）。issue からはリンクする。レコードは intent、criteria、limits、decision、invalidation、outcome を持つ。

| 消費者 | 何に使う |
| --- | --- |
| レビュー | criteria のカバレッジと limits を見る |
| 進捗 | 証拠カバレッジ、done level、停滞を集計する |
| 次セッション | 意図・判断・無効条件を読む |
| 製品 | import / export（後続） |

**消費者がいない欄は作らない。** 使われない記録は、書かれない記録よりも悪い。done level はレコードから導出する。閉じるレベルはレコードに書き（L2 / L3 / L4）、探索と納品で合格ラインを変える。移行は新規からで、過去は遡及しない。

詳細と未確定は [0195](../issues/0195-work-record-contract.md)。

### 3.3 レビューを4層に分ける

既存の review.md は実装レビューの規程として維持する。その上で、層を明示して呼び分ける。

| 層 | 問い | 成果物 | いつ | 主担当 |
| --- | --- | --- | --- | --- |
| 意図 | 誰のどの課題か。テーゼと整合するか | レコードの intent | 実装前 | 人間 |
| 設計 | どう解くか。代替案と制約は妥当か | 設計節 / ADR | 実装前 | reviewer |
| 実装 | 意図どおり動くか。壊していないか | diff・テスト | 実装中 | reviewer |
| 結果 | 成果が出たか。学びは残ったか | デモ・指標・判断ログ | 統合後 | 人間 |

予算は既存のまま。reviewer は同時に1レーン、レビュー待ちはリードタイムの半分以下。AI 一次レビューを入れるなら、先に自チームのゴールデンセットで precision を測る。ノイズの多いレビュアーは注意力を殺す。

### 3.4 月次15分：判断の蒸留

先月のレビュー指摘から3つだけ選び、次のどれかに落とす。

- AGENTS.md / 設計ルール（判断基準）
- anti-slop / lint ルール（機械で防ぐ）
- テスト / eval（実行で防ぐ）
- decisions（判断として残す）

落とせないものは「なぜ今は決めないか」を decisions に書く。件数を成果にしない。**再発が減ったか**だけを見る。

### 3.5 週次デモと月次キルリスト

- 週次30分：PoC か実環境を動かす。資料を読まない。動くものを見て、残すか殺すかを決める。
- 月次：plan から降ろすもの、捨てるものを決める。キルリストを BOARD に1行残す。

やらないことを決めないと、強みに時間が戻らない。

### 3.6 agent への委任の設計

agent に渡す前に、次を揃える。揃っていない委任は、レビューで決め直すことになる。

- **Intent と受入基準**：何のために、何が満たせれば合格か。
- **touches と done-level**：触ってよい範囲と、閉じてよいレベル。
- **判断基準**：AGENTS.md / rules / 既存の設計。暗黙の好みを渡さない。
- **証拠の要求**：テスト、実行結果、デモ。完了報告だけを受け取らない。

Proof of Done の原則を借りれば、**agent の報告は有用なインターフェースだが、真実の源ではない**。確認は証拠で行う。同じ指摘が2回出たら、次は口で言わずルールにする。

### 3.7 計測（既存 + 4）

| 指標 | 定義 | 置き場 | 警報 |
| --- | --- | --- | --- |
| リードタイム | ブランチ開始から merge | LANES | 2日超 |
| レビュー待ち | 依頼から PASS | LANES | リードタイムの半分超 |
| 統合待ち | PASS から merge | LANES | ゲート1回分超 |
| 競合 | merge 時のコンフリクト | LANES | 5回に1回超 |
| ゲート時間 | npm run check | LANES | 現在の2倍超 |
| 統合後の失敗 | main が赤になった回数 | LANES | 0 以外 |
| 証拠カバレッジ | 構造化レコードに Evidence がある割合 | 月次 | 50%未満 |
| 手戻り率 | 差し戻し・再作業の割合 | 月次 | 上昇傾向 |
| 判断リードタイム | 論点が出てから決まるまで | 月次 | 1週間超 |
| Moat 配分 | Moat 作業に使った時間 | 四半期 | 10%未満 |

数値は目標ではなく警報。超えたらレーンを増やすのではなく、ボトルネックを直す（既存の原則）。

## 4. 役割

| 役割 | 決めること | やらないこと |
| --- | --- | --- |
| 人間 | テーゼ、優先度、受け入れ、キル | 実装の細部 |
| lead（統合） | 統合順、BOARD / LANES、判断ログ、蒸留 | 製品コードを書くこと |
| worker（agent） | 実装と証拠 | 優先度の昇格、意図の変更 |
| reviewer（agent） | 独立レビュー、PASS / FAIL、再発防止の提案 | 実装を直すこと |

原則は2つ。**実装とレビューを分ける**（既存）。**判断と実行を分ける**（追加）。判断を実行側に戻すと、レビューは「決め直し」になり、量が増える。

## 5. アンチパターン

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| ゲートが緑なので成果も出ている | 完了が L3 で止まっている | Result に Evidence と Limits を書く |
| issue 数・PR 数を進捗と呼ぶ | 出力量が成果の代理になっている | L4 の件数と Moat 配分を見る |
| レビュー待ちが長いのにレーンを増やす | ボトルネックがレビュー | レーンを減らすか、レビューを分担する |
| 決定がチャットに消える | 記録の習慣がない | decisions に1行でよいから書く |
| 効率化で浮いた時間が機能追加に消える | 再投資先が未定義 | 四半期に Moat 配分を決める |
| 証拠集めが重くてレビューが増える | 証拠を手作業で作っている | 自動収集を優先し、L4/L5 は任意にする |

## 6. 90日

| 期間 | やること | 成果物 |
| --- | --- | --- |
| 第1〜2週 | ベースライン測定（既存指標 + 証拠カバレッジ + 手戻り） | 1枚の表 |
| 第3〜4週 | テーゼと Moat 台帳、issue テンプレートに Intent | work/THESIS.md、テンプレ案 |
| 第5〜8週 | Result の Evidence pack、レビュー4層、AI 一次レビューの評価 | 運用ルール |
| 第9〜12週 | 週次デモ、月次キルリスト、判断の蒸留、四半期レビュー | 定例と記録 |

## 7. 採用した決定

- **D067** 完了は構造化レコードで表し、Result への追記をやめる。
- **D068** 四半期のテーゼと Moat 台帳を持ち、成果の層を運用に入れる。
- **D069** レビューを4層に分け、月次で判断を蒸留する。

いずれもプロセスの追加ではなく、既存の器（issue / Result / decisions / LANES）への欄の追加である。形式と未確定は [0195](../issues/0195-work-record-contract.md) で決める。

## 8. 製品設計との関係

この運用は、そのまま hns の製品モデルになる。issue = WorkItem、Result = Evidence、D = Decision。**hns 自身の開発が、最初の利用者（dogfooding）になる。**

製品側の設計は [product-record-design.md](product-record-design.md) に置く。
