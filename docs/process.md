# 開発プロセス（調査 → 要件 → 技術選定 → 設計 → リリース）

2026-11-07 / D045。工程の境界を明確にし、未確定が残っていても合理的に前へ進むための進め方。
ゲートは停止装置ではなく、**次に進む範囲・残す課題・制約を決める場**。設計の判断は [design.md](design.md)、
実装後の検証は [review.md](review.md)、記録は [decisions.md](decisions.md) と work/ に置く。

## 原則

1. **必要十分な確定**を目指す。全体の100%は要求しない。次にやる作業に必要なことを優先して決める。
2. 確定度は**事項ごとに違ってよい**。機能Aは詳細設計、機能Bは要件検討、を並行してよい。
3. **重大リスクだけ**を実質的なブロッカーにする（安全・法令・セキュリティ・不可逆な投資）。
4. 未確定は放置せず、**仮説・影響・責任者・期限・トリガー**を記録する。
5. 判断権限を明確にする。承認者は「全部に同意する人」ではなく「許容するリスクと次の投資を決める人」。
6. 進捗より**学習**を優先する。不明点は小さな調査・試作で減らし、結果で計画を更新する。

## 段階と出口

入口・出口は「全対象が完成」ではなく、**次の着手範囲を判断できる状態**を指す。

| 段階 | 次に進む条件（出口） | 記録先 |
| --- | --- | --- |
| 企画 | 目的・最初の対象・成功の測り方を説明できる | README（要件） |
| 要件 | 次に設計する機能の利用目的・シナリオ・制約・受入観点が決まり、未確定の扱いが合意済み | README / work/issues |
| 基本設計 | 対象領域の境界と契約、非機能の方針、リスクの高い仮説の検証計画がある | design.md / decisions |
| 詳細設計 | 着手タスクが実装・レビュー・テスト可能で、残る判断は実装中に安全に解消できる | work/issues |
| 実装 | 統合対象の変更が review PASS で、必要なテストに合格している | review.md / commit |
| 結合 | 次に渡す連携範囲の重要フローが動き、未解決が次段階を無効にしない | issue の Result |
| システム | リリース候補の必須シナリオと非機能の結果があり、残リスクが業務側に示されている | issue の Result |
| 受入 | 今回リリースする範囲の必須業務が成立し、受入可否を判断できる | issue の Result |
| リリース | 移行・監視・障害対応・切戻しが実行可能で、重大リスクの受容が明示されている | issue / decisions |
| 運用 | 運用責任・保守体制・残課題の移管先が決まっている | BOARD / issue |

工程は重なってよい。ただし、各作業の状態・前提・承認範囲は追跡できるようにする。

## ゲート判定

| 判定 | 意味 | 扱い |
| --- | --- | --- |
| Go | 次の予定範囲を進めてよい | 通常進行 |
| 条件付き Go | 未確定はあるが、対策・責任者・期限・制限を置けば進める | 範囲と条件を追跡 |
| Limited Go | 全面は早いが、調査・試作・低依存部分なら着手できる | 許可した作業だけ実施し、再判定 |
| Hold | その作業で許容できない損失・リスクが生じ得る | **影響する作業だけ**止める。全体停止にしない |

ゲートで確認する5点:

1. 次に何をするか（対象・作業・期間）が決まっているか。
2. 着手に必要な情報があるか。無い場合も仮説や検証方法で代替できるか。
3. 未確定の影響（手戻り・顧客影響・費用・セキュリティ・外部依存）は許容できるか。
4. 誰がいつ決めるか（責任者・期限・判断材料）が決まっているか。
5. 戻れるか（設計変更の余地・検証点・停止条件）があるか。

**Hold の目安**: 法令・契約・個人情報・重大セキュリティの未評価、取り返せない変更や本番影響、
外部IFやデータ契約が未確定で依存実装が大規模に手戻る、検証環境や安全対策が無い、目的・責任者・完了条件が不明。
逆に、文言・優先度の低い操作・将来の拡張仕様は、影響が限定的なら確定を待たずに進める。

## 未確定の管理

状態は4つに分ける。**未確定そのものは問題ではない。未管理が問題。**

| 状態 | 意味 | 扱い |
| --- | --- | --- |
| 決定 | 決めて記録した | decisions に書く |
| 仮決め | 暫定で進める | 仮説と再判定トリガーを台帳に書く |
| 未決定 | まだ決めていない | 責任者・期限・影響を台帳に書く |
| 対象外 | 今回やらないと決めた | 理由を1行残す |

台帳の最小列: `ID / 未確定 / 現時点の仮説 / 影響する作業 / リスク / 決定責任者 / 期限かトリガー / 暫定対応`。
高リスクは毎週か関連作業の着手前に再評価する。期限超過でも全工程を止めず、影響するタスクだけ再判定する。
「解決」は確定だけでなく、**対象外化・後続送り・検証によるリスク受容**も含む。

## 調査の進め方

技術を選ぶ前に、短い問題文を書く。

- 誰の、どの場面か（「企業の従業員」ではなく「毎週、複数部署の依頼を振り分ける担当者」）。
- 現在の行動は何か（道具・手作業・代替手段・諦めている場面）。
- 何が改善すれば成功か（機能ではなく、達成できること・減らす負担）。
- なぜ既存の方法では足りないか。
- 今回の制約（時間・技能・費用・既存データ・連携・守る約束）。

参考は**三つの層**で探し、「どの問題をどう解いているから参考か」を一文添える（URL だけにしない）。

1. 同じ課題を解く製品・現在の業務 — 既存の解法と、解けていない部分。
2. 隣接分野の優れた体験 — 絞り込み・編集・共有・承認・復旧の操作パターン。
3. 実装できる部品 — SDK・ライブラリ・デザインシステム・管理サービス（採用条件も）。

比較は汎用の機能表ではなく、**代表的な1件**を最後まで通して行う。主要な仕事が終わるか、設定で使えるか、
現在の制約（権限・データ・連携・環境）に合うか、誰が維持するか、費用の増え方、資産を取り出せるか。
**調査の前に「何が分かれば判断が変わるか」を書く**。候補と自前案の違い・採否条件・残る不明点を説明できたら止める。

**課題と解決策を混ぜない。**「検索画面を作る」は解決策、「過去の決定を見つけられない」が課題。
この段階の終了条件は「現状より何が良くなるか」と「自前で作る理由」を説明できること。既存品で足りるなら、作らずに終える。

## 全体像

三つの視点を、矛盾しない粗さで揃える（三冊の設計書にはしない）。

- **体験**: きっかけ → 開始 → 入力・判断 → 待ち・受け渡し → 完了の知らせ → 失敗からの再開。
- **概念**: 主要なもの・関係・主体と権限・状態・崩してはいけない規則・正本はどこか。
- **システム**: 外側（利用者・自システム・連携先）と内側（アプリ・保存先・非同期・外部）。箱には責任・流れる情報・
  誰の権限か・止まったときに何が困るか・自前か既存品かを添える。

品質は利用場面とセットで決める（「高速」ではなく「どの操作で待ち時間が仕事を妨げるか」＋水準＋確認方法）。
一般的な水準を根拠なく持ち込まない。

## 技術選定

**変更コスト × 不確実性**で扱いを変える。固定的に「DBは難・UIは易」と決めない。変更の負担は
コード・保存済みデータ・外部への作用・人と組織への約束の4つで見る。

|  | 判断材料が揃っている | 不足している |
| --- | --- | --- |
| 変更の負担が小さい | 早く決めて進む | 小さく試す |
| 変更の負担が大きい | 代替案と影響を確認し、理由を記録して決める | **先に調査・試作**。確定を待てるか、変更を容易にできるかも見る |

選定の順序は **買う → 借りる（既存品・サービス）→ 作る**。自前は、利用者から見た価値の核と、境界の制御が要る部分に絞る。
初期費用と運用費用を分けて見る。依存は許容しつつ、失いたくない資産（データ・履歴・権限・移行経路）を守る。

試作と実用版を区別する。試作は「何が分かれば判断が変わるか」を先に決め、結果を全体像へ戻す。
不確実性が高いことだけを理由に全部を調査しない。今使わず、遅らせても困らない機能は保留できる。

**決定と保留の記録**:

- 決定: 文脈 / 選択肢 / 決定と理由 / 結果 / 変更するとき / 見直し（decisions の形式）。
- 保留: 何を決めていないか / 仮説 / 影響 / 再開条件（日付かイベント） / 責任者。
- 比較: 代表1件で、主要な仕事・設定で使えるか・制約・維持・費用・資産の取り出し。

```markdown

- 条件・制限:
```

