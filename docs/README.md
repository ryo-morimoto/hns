# docs の使い方

- 更新日: 2026-11-06

## 1. 置き場所

| 置き場所 | 入れるもの | 例 |
| --- | --- | --- |
| `sources/` | ユーザー提供資料の原文。**改変しない** | レポート、開発プロセス、プレイブック |
| `requirements/` | 要件・確定事項・未決事項の状態記録。版単位で不変 | `requirements-design-state-v0.3.md` |
| `research/` | 調査・検証の結果。**時点記録** | 実APIの確認、適合テストの結果 |
| `design/` | 設計・契約。**生きた文書** | アーキテクチャ、Workspace契約 |
| `decisions/` | ADR。**決定の記録** | 版の固定、境界の採用 |
| `plan/` | 現在地・ロードマップ。**生きた文書** | `now.md`, `roadmap.md` |

- リポジトリ直下や `docs/` 直下に新しい `.md` を作らない。まずこの表で置き場所を決める。
- 図・試作・検証コードは `poc/` に置き、文書からリンクする。

## 2. 文書の性質

| 性質 | 場所 | ルール |
| --- | --- | --- |
| 原文 | `sources/` | 一字も変えない。誤りは注記を別文書に書く |
| 時点記録 | `research/`, `decisions/` | 書いた後に**本文を書き換えない**。続きは新番号、決定の変更は新ADRでsupersede |
| 生きた文書 | `design/`, `plan/` | 現状と一致させる義務がある。本文を変えたら冒頭の更新日を今日にする |

要件の変更は、`requirements/` の次版（v0.4）として新しいファイルで行う。v0.3 は残す。

## 3. 書き方

- 事実・推論・未確認を分けて書く。根拠が外部資料なら出典を、実測なら再現手順を添える。
- 数値・日付は「いつの情報か」を書く。
- 未確定は消さずに、担当・期限または再開条件を書く（開発プロセスの未確定事項台帳に合わせる）。
- 決定は `decisions/` に、文脈・選択肢・決定・結果・**見直す条件** を書く。

## 4. まだ無いもの

- 用語lint・リンク切れ検査（fps-hns で使っている `npm run check` 相当）
- タスク管理（backlog.md CLI を使うかは未決、U-16）
